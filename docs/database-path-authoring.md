# Authoring Database Zero to Master

## Source of truth and publication

The public Database Engineering path is `/learn/database-engineering`; its SQL/database curriculum retains the source name Database Zero to Master. Transaction practice shares that page without changing its existing lesson or lab IDs.

The canonical package is `curriculum/taalmo-database-zero-to-master/`. The adapter `src/content/database/catalog.ts` preserves all blueprint IDs, titles, order and module prerequisites. Adding an authored record in a registered content JSON file makes that canonical lesson published. Incomplete authored records must not be added. The historical validation workflow below applies only with explicit user authorization; current AGENTS.md prohibits running tests, audits, SQL validation, manual/browser checks, lint, typecheck and build. Unauthored lessons remain draft, visible as roadmap entries without links; the lesson route uses the published static parameter list only.

Published content covers L0–L4 and L5M01–L5M04: 24 modules, 72 lessons. The remaining 48 lessons are explicitly draft; see `database-path-remaining.md`. Catalog imports do not write learner storage or reset progress. Content after L2M01 has source/diff review only, with SQL and browser behavior unexecuted.

## Content contract

Use `src/content/database/types.ts`. Each authored lesson includes stable ID and semantic content version, difficulty (`beginner` for L0–L1, `intermediate` for L2–L5M04)/tags, a unique real problem, measurable objectives, substantial Indonesian explanation with misconceptions and limits plus a complete authored English display translation, worked PostgreSQL SQL with expected columns/rows, two or more concept checks, two practice variants, two independently graded edge cases, three progressive hints, a reference solution and reflection.

Questions use stable IDs, distinct option texts, an answer index and feedback for every option. Correct positions should vary. Retakes rotate visible options while retaining the canonical answer index. Practice variants change the scenario or result being reasoned about; change numeric inputs and their correct feedback together. Keep remedial feedback specific to the error, including the concept to revisit. Mark safety/integrity questions critical and mark the corresponding activity critical. All activity/edge-case answers must be correct to finish a lesson.

All published learner-facing text must have English and Indonesian display copy. Keep canonical IDs, versions, SQL, fixture/result values, question order and numeric answer indexes unchanged. Add normalized source-string keys and full English translations in the appropriate `src/content/messages/en-database-*.json` dictionary; register a new dictionary in `src/content/messages.ts`. Cover hooks, objectives, every section paragraph/title, worked explanations, all question/options/feedback/explanations, practice/setup, hints, solution explanation and reflection prompt. Catalog titles/goals/objectives, draft lesson titles, labels and flow descriptions require translations too. Source-English UI labels need Indonesian entries. Do not pass SQL scripts or expected rows through the translator, and do not translate learner-entered reflection. Localize display values without changing React keys or persistence keys. A fallback to source text is not complete localization.

The new player reuses the platform Quiz, Button, Workspace and local progress repository. Current exercise fallback is an output prediction or debugging decision. It does not execute learner SQL or establish arbitrary SQL-writing skill. Reflection is stored, not automatically graded for quality. Do not publish a lesson requiring unavailable interactive evidence by representing its title as a completed lab.

## PostgreSQL fixture and examples

Target: PostgreSQL 17; earlier L0–L2M01 examples were verified locally with `postgres:17-alpine`. School Finance seed has six students, ten invoices and eleven payment rows. Only succeeded payments count as receipts. It deliberately has no `invoices.status` column and no identity/default for `students.student_id`.

For generated IDs or mutations, specify an isolated TEMP-table setup. Explain the adaptation in learner copy. `worked.sql` returns a table described by `columns` and `rows`; expected CSV values are strings or null. Use `ordered: true` only when ordering is part of the exercise contract. Otherwise verification compares multisets, including duplicates. Amount formatting and deterministic dates must match the example. Avoid current date/time and environment-dependent formatting.

`activity.solutionSql` is a reference script, not executed by the website. An intentional rejection must carry `solutionError` with its PostgreSQL SQLSTATE, and explain why the rejection is expected. Every other reference script must run without error. Setup applies to both worked example and reference solution on separate fresh fixtures.

```sh
npm run curriculum:audit
npm run curriculum:sql -- --context colima
```

No application seed command is necessary: catalog imports are static. SQL verification alone seeds a disposable database. It requires Docker with a locally available `postgres:17-alpine` image and Python 3; substitute your Docker context for `colima`. It creates its own randomly named container with no network, no host mount, no exposed port and bounded resources. It refuses a database URL by offering none. Container and anonymous volume are removed in `finally`; no existing database/container is reset. The source SQL seed drops fixture tables and must never be run against production.

Primary references: [PostgreSQL NULL comparisons](https://www.postgresql.org/docs/17/functions-comparison.html), [table expressions and joins](https://www.postgresql.org/docs/17/queries-table-expressions.html), [identity columns](https://www.postgresql.org/docs/17/ddl-identity-columns.html), [ROLLBACK](https://www.postgresql.org/docs/17/sql-rollback.html), [subquery expressions](https://www.postgresql.org/docs/17/functions-subquery.html), [CTEs](https://www.postgresql.org/docs/17/queries-with.html), [set operations](https://www.postgresql.org/docs/17/queries-union.html).

L2M02 references: [window tutorial](https://www.postgresql.org/docs/17/tutorial-window.html), [ranking and offset functions](https://www.postgresql.org/docs/17/functions-window.html), [window ordering and frames](https://www.postgresql.org/docs/17/sql-expressions.html#SYNTAX-WINDOW-FUNCTIONS). Examples preserve payment detail, aggregate to student grain before ranking, and aggregate invoice receipts before monthly windows. Monthly totals allocate all known successful receipts to invoice periods; they are not historical month-end cash-flow snapshots. Missing calendar months and opening balances are not invented.

L2M03 references: [date/time types](https://www.postgresql.org/docs/17/datatype-datetime.html), [date/time operations](https://www.postgresql.org/docs/17/functions-datetime.html), [series generation](https://www.postgresql.org/docs/17/functions-srf.html), [join semantics](https://www.postgresql.org/docs/17/queries-table-expressions.html), [CASE and COALESCE](https://www.postgresql.org/docs/17/functions-conditional.html). Receipt filters use half-open boundaries in Asia/Jakarta. The 2026 calendar includes twelve months, with LAG applied after zero filling. Aging uses 10 October 2026 and receipts before the following local midnight, assumes fixture invoices are already issued, distinguishes not_due, and reports only positive outstanding. The fixture lacks a full historical ledger; missing timestamps, credits and completeness of live data need separate treatment.

L2M04 references: [SELECT and DISTINCT](https://www.postgresql.org/docs/17/sql-select.html), [subquery expressions](https://www.postgresql.org/docs/17/functions-subquery.html), [EXCEPT ALL and compatible results](https://www.postgresql.org/docs/17/queries-union.html), [constraint scope](https://www.postgresql.org/docs/17/ddl-constraints.html). Teach invoice versus payment grain, preaggregation, correlated anti-joins and right/left NULL limits. The NULL-bearing list is a CTE, preserving the fixture's NOT NULL foreign key. The checkpoint compares all four expected report columns in both directions with EXCEPT ALL and separately exposes negative balances. Its proposed-payment CASE is a read-only decision, not an atomic write guard; the seed does not reject cross-row overpayment. No test suite was expanded or executed to teach the query-testing topic.

L3M01 keeps the blueprint's mixed examples: Commerce entities/lifecycle, a student–guardian N:M exercise, and eight School Finance payment invariants. The Commerce mini fixture and guardian extension are canonical inline `worked.setupSql` definitions in `l3-modeling.json`; they create TEMP tables without mutating School Finance. TEMP FKs reference explicit `pg_temp` tables; guardian students are copied from the seed rather than referenced by a TEMP-to-permanent FK. An optional translated `worked.dataset` overrides the historical School Finance description. Register structural diagrams in `modeling-schemas.ts`: use the shared schema-table renderer, explicit PK/FK/types and cardinality, plus text explaining optionality and unimplemented guards. Diagram pairs may repeat the same entity to make branching relationships readable; they do not duplicate data.

L3M01 references: [PostgreSQL constraints](https://www.postgresql.org/docs/17/ddl-constraints.html), [temporary table semantics](https://www.postgresql.org/docs/17/sql-createtable.html), [schema qualification](https://www.postgresql.org/docs/17/ddl-schemas.html). The eight school invariants separate observed counts from guards: I1–I5 enforced in the seed, I6 missing timestamp CHECK, I7 missing atomic aggregate guard, I8 missing callback business identity. I8's observed count is NULL because the evidence is unavailable. The reference INSERT's expected SQLSTATE 23514 comes only from proposed I6 on a TEMP table; it does not establish overpayment rejection or callback idempotency. These are prediction/design-reasoning exercises, not an interactive ERD editor or SQL-writing certification. L3 assessments follow the existing all-modules-published and mastery gates.

L3M02 uses independent inline TEMP fixtures in `l3-normalization.json`, preserving canonical IDs and L3M01 examples. The invoice-list example contrasts curated data with legacy TEXT, not an automated migration parser; relational identity and FK ownership replace hidden references without claiming every TEXT/JSON value violates 1NF. The order example declares current-name dependencies, retains agreed item prices, and reconstructs through PK/FK. Explain 2NF over every candidate key, 3NF's prime-attribute exception, and BCNF's stronger determinant rule; the customer/region/rep example explicitly separates lossless decomposition from dependency preservation. New structural diagrams reuse `modeling-schemas.ts` and the existing 1–0..N renderer.

L3M02 references: [Database System Concepts relational design](https://www.db-book.com/Previous-editions/db5/slide-dir/ch7.pdf), [RPI normalization definitions](https://www.cs.rpi.edu/~sibel/csci4380/fall2026/lecture_notes/lecture5.html), [Aalto anomaly/normal-form teaching](https://opencs.aalto.fi/en/courses/databases/part-8/4-normalization), [PostgreSQL materialized views](https://www.postgresql.org/docs/17/rules-materializedviews.html). In the cache fixture, item quantity × agreed unit price is authoritative; cached_total is nullable derived data. NULL differs from zero, empty orders must remain in reconciliation, and moving an item affects both old/new aggregates. Reference replacement is repeatable only for the stated unchanged, isolated input; it implements no online invalidation, writer protocol, trigger, or version guard. Do not turn the example into a claim that denormalization improves measured performance or that the batch script guarantees concurrent financial correctness. L3 availability follows the published-module gate.

L3M03 (`l3-types-constraints.json`) uses isolated TEMP key-scope, student-period and payment-event fixtures. Identity PKs do not replace scoped business UNIQUE constraints, and explicit IDs do not imply sequence max+1. UNIQUE student-period compares exact DATE values: first-of-month remains an input contract unless separately constrained. Provider-local references require merchant scope. The reference duplicate student-period INSERT expects 23505; the NaN INSERT expects 23514 from an explicit NaN/amount CHECK. NUMERIC rounds to declared scale before the check; timestamp displays use explicit AT TIME ZONE rather than session defaults. Diagrams are registered through types-constraints-schemas.ts with 1–0..N relationships. PostgreSQL references: [constraints](https://www.postgresql.org/docs/17/ddl-constraints.html), [numeric](https://www.postgresql.org/docs/17/datatype-numeric.html), [date/time](https://www.postgresql.org/docs/17/datatype-datetime.html).

L3M04 (`l3-evolution.json`) keeps status mapping, address expand/backfill and student-address reconciliation in isolated TEMP fixtures. Baseline rows are copied before migration; per-identity FULL JOIN counts use IS DISTINCT FROM. The eight-column output is an aggregate summary, not a per-row investigation list. Delimiter/sentinel checksum serialization is explicitly illustrative and ambiguous outside the curated input; real audits need canonical encoding and exact comparisons. Missing student99 in the FK-backed patch is rejected with23503 before reconciliation. The address nonempty CHECK trims whitespace. A fresh reference repeats column-add/backfill preparation before NOT VALID/VALIDATE and intentionally expects23514 for the still-missing address. No production schema, writer, lock or deployment was changed. References: [ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html), [rollback](https://www.postgresql.org/docs/17/sql-rollback.html).

L4M01 (`l4-acid.json`) uses isolated TEMP account/ledger fixtures. The transfer performs two UPDATEs in BEGIN/COMMIT and emits one final SELECT; accounts100000/50000 become70000/80000 with total150000. TEMP data cannot establish crash durability. The ledger classifier requires exactly two entries, distinct accounts, one negative debit, one positive credit and net zero; it is an authored read report, not an installed cross-row guard. The SAVEPOINT example rolls back the optional fee while preserving the prior capture and emits one resultset. Timeout at COMMIT can leave an unknown outcome requiring reconciliation; database rollback does not undo external provider effects. References: [transactions](https://www.postgresql.org/docs/17/tutorial-transactions.html), [savepoints](https://www.postgresql.org/docs/17/sql-savepoint.html), [rollback to savepoint](https://www.postgresql.org/docs/17/sql-rollback-to.html).

L4M02 (`l4-isolation.json`) uses explicitly authored VALUES traces as prediction inputs, not observed concurrent PostgreSQL output. Given the stated intervening commit, RC reads100000 then125000, RR/Serializable retain100000. In the RR own-write example, B changes invoice501 after A snapshot; A still reads open on501 and writes an untouched DIFFERENT502 to review. Attempting to update501 instead raises40001 and requires restarting the transaction. FOR UPDATE/NOWAIT/SKIP LOCKED compare waiting/error/omitted locked501 and free502 as an authored candidate, not an actual durable claim. A skipped/empty result does not establish no outstanding work. References: [transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html), [explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html).

L4M03 (`l4-concurrency.json`) declares READ COMMITTED for the conditional-debit schedule:100000 minus70000 yields30000; the second debit affects zero rows and must not be treated as successful. RR/Serializable may instead require40001 retry. Two-doctor write skew uses different rows and distinguishes RR from Serializable; the chosen B victim is illustrative. Deadlock40P01 and lock-acquisition timeout55P03 differ from statement completion unknown40003 or generic network failures after COMMIT. Retry restarts the whole transaction and remains bounded; unknown completion needs business-key reconciliation. Single-session TEMP reference scripts are not concurrent-engine evidence. References: [isolation](https://www.postgresql.org/docs/17/transaction-iso.html), [UPDATE](https://www.postgresql.org/docs/17/sql-update.html), [locking](https://www.postgresql.org/docs/17/explicit-locking.html), [error codes](https://www.postgresql.org/docs/17/errcodes-appendix.html).

L4M04 (`l4-payments.json`) uses scoped merchant/business keys and toy payload fingerprints/signature-valid flags, not provider authentication code. Same-payload replay preserves the local marker; the report distinguishes payload_conflict from no incoming callback without overwriting a successful payment. The double-entry wallet convention reconstructs balances 55000/95000; append-only behavior and atomic cross-table effects still require writer policy. The duplicate-delivery script uses two separate INSERT statements, then a final SELECT: the second same-key/payload delivery exercises the conflict branch and leaves one local effect. It demonstrates sequential fixture replay, not concurrent execution or external exactly-once delivery. References: [INSERT/ON CONFLICT](https://www.postgresql.org/docs/17/sql-insert.html), [data-modifying CTE snapshots](https://www.postgresql.org/docs/17/queries-with.html).

L4M05 (`l4-side-effects.json`) writes payment and outbox in one explicit transaction, then reads their pairing in a separate statement. TEMP tables illustrate atomicity, not crash durability or broker delivery. The worker report classifies authored lease/payload states without executing a claim, publishing or installing consumer deduplication. The concurrency checkpoint compares authored candidate summaries against a 100-debit rubric; flags and result labels are inputs, not trusted or observed multisesion evidence. Completing L4 publication exposes its assessment through the existing all-modules-published gate. References: [transactions](https://www.postgresql.org/docs/17/tutorial-transactions.html), [RETURNING](https://www.postgresql.org/docs/17/dml-returning.html), [SELECT locking](https://www.postgresql.org/docs/17/sql-select.html).

L5M01 (`l5-planner.json`) stores explicitly authored plan nodes, timing/buffer illustrations and before/after estimate fragments in isolated TEMP tables. These are deterministic reading exercises, not EXPLAIN output measured from the fixture. Parent/child relationships and inclusive buffer accounting remain internally consistent. Explain cost units versus milliseconds, per-loop actual rows/timing, nonadditive parent/child totals, and shared reads versus physical disk reads. Plain EXPLAIN plans; EXPLAIN ANALYZE executes the statement, while ANALYZE updates statistics. The skew fixture has eight VIP rows out of ten and does not force the depicted plan choice. References: [using EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html), [planner statistics](https://www.postgresql.org/docs/17/planner-stats.html).

L5M02 (`l5-indexes.json`) separates index eligibility and authored workload metadata from actual planner choices or benchmark output. Selectivity is explicitly matching rows divided by total rows. Composite leading-key behavior targets PostgreSQL17: filtering only due_date on (student_id, due_date) may require a full index scan and does not supply global due_date order. INCLUDE columns are payload rather than search keys, and index-only scans still depend on heap visibility. Partial predicates must be implied by the query; parameterized predicates do not automatically establish that implication. Additional invoice fields belong only to isolated fixtures, not to the School Finance seed. Index storage and maintenance costs are workload tradeoffs; do not remove integrity indexes solely for write speed. References: [multicolumn indexes](https://www.postgresql.org/docs/17/indexes-multicolumn.html), [index-only scans](https://www.postgresql.org/docs/17/indexes-index-only-scans.html), [partial indexes](https://www.postgresql.org/docs/17/indexes-partial.html).

L5M03 (`l5-joins-rewrite.json`) uses authored join-candidate and sort-case tables for resource reasoning, without executing plans or measuring spill. work_mem is per executor operation, not a connection/process memory ceiling; hash_mem_multiplier and parallel/concurrent operations matter. SET LOCAL is an illustrative bounded command, not a measured tuning change. The rewrite copies ten School Finance invoices and eleven payments into isolated TEMP tables, preaggregates only succeeded payments, preserves invoices without receipts through LEFT JOIN and exposes payment count, paid and outstanding. Its reference compares all six result columns in both directions with EXCEPT ALL; equivalence on this fixture does not prove universal equivalence or improved performance. References: [EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html), [resource memory](https://www.postgresql.org/docs/17/runtime-config-resource.html), [set operations](https://www.postgresql.org/docs/17/queries-union.html).

L5M04 (`l5-large-data.json`) generates 100 deterministic events across 100 declared tenants: tenant 1 owns 90 events (1% of tenants, 90% of rows), ten small tenants own one each. The million-row generator is an unexecuted design, not a scale benchmark. Pagination uses NOT NULL created_at plus a unique ID, descending total order and a strict tuple cursor; a shared fixture makes offset and keyset show 1005/1004/1003. The worked ROW_NUMBER columns decorate the comparison, while the reference uses the direct seek query; no speed claim follows. Keyset does not freeze a cross-request snapshot, and reverse traversal can use a compatible backward B-tree scan. Batch metadata assumes one transaction per chunk and illustrates different rollback scopes; unknown commits require identity reconciliation. References: [LIMIT/OFFSET](https://www.postgresql.org/docs/17/queries-limit.html), [row comparisons](https://www.postgresql.org/docs/17/functions-comparisons.html), [index ordering](https://www.postgresql.org/docs/17/indexes-ordering.html).

## Progress, gates and versions

`taalmo.progress.v1` retains the original transaction milestones. Its optional `curriculum` field stores versioned lesson/exam records and a resume ID for the current browser learner. Saved answers use canonical option indexes; translated or reordered display copy does not change grading. Completed snapshots remain when starting a fresh attempt. New content versions requalify against their own records without deleting older versions.

A lesson requires the selected practice variant, every edge case, all concept checks and a recorded reflection. Prerequisite modules gate official completion, while all published theory remains explorable. Module checkpoint needs all lesson activities and >=80%, including every critical question correct. Level assessment needs all modules and >=85%, including critical questions correct. Assessment scores are derived from saved answers rather than trusting a stored percentage. No week/calendar lock exists. Diagnostic only recommends a starting topic and never grants progress or bypasses safety.

This is formative device-local mastery, not protected credential issuance. Answers exist in client content; expected solutions are concealed in the UI until a practice submission. There is no server grading, authentication, cross-device progress, tenant database or trusted badge service. Introducing those requires a separate backend design; do not claim browser storage prevents learner tampering.

2. Register each new content file in the catalog, content audit, SQL verifier and browser integration imports. Run the content audit; fix missing body, invalid question IDs/answers, incomplete feedback, missing variants/edge cases/hints or broken prerequisites.
